# Draw call 및 메시 재사용 개선 보고서

작성일: 2026-09-22. 상태: 소스 구현 완료, 변경 후 사용자 빌드·실측 대기.

## 1. 제공받은 기준 로그

| 샘플 | FPS | 최근 프레임 호출 | 구간 평균 호출 | 최소 | 최대 |
|---|---:|---:|---:|---:|---:|
| 1 | 42.0 | 170 | 177.7 | 170 | 180 |
| 2 | 50.0 | 178 | 178.5 | 170 | 184 |
| 3 | 52.5 | 168 | 177.8 | 168 | 184 |
| 4 | 57.0 | 168 | 170.2 | 168 | 172 |
| 5 | 52.7 | 168 | 168.0 | 168 | 168 |
| 6 | 56.5 | 168 | 168.0 | 168 | 168 |

이 로그만으로 GPU 병목이나 draw call이 FPS 저하의 직접 원인이라고 확정할 수 없다. FPS는 42.0~57.0, 호출은 구간 전체 기준 168~184다. 마지막 두 구간은 호출 수가 같아도 FPS가 다르다. 하드웨어, 빌드 종류, 장면, 후처리 설정은 기록되지 않았으므로 새로운 결과와의 정밀 비교에는 추가 측정이 필요하다.

## 2. 코드에서 확인한 기존 비용

1. 기존 Renderer도 삼각형을 모아 제출했다. 다만 연속 요청의 텍스처가 같을 때만 합쳤다. 단색용 흰 텍스처와 문자열별 GDI 텍스처가 교차하면 새 배치가 만들어졌다.
2. `Ellipse`는 매번 20개 삼각형, 60개 정점을 생성했다. `Glow`는 원을 6개 겹쳐 360개 정점을 생성했고 원의 각도마다 CPU 삼각함수를 계산했다.
3. 좌표·색·UV·발광을 모든 정점에 복제하여 프레임마다 VBO에 업로드했다. 기존 Vertex는 float 9개, 36바이트였다.
4. 블룸·가장자리 블러·합성은 서로의 결과를 읽는 별도 패스다. 후처리 호출은 일반 도형 배치와 합칠 수 없다.
5. 게임 타이머는 16ms로 재등록하며 업데이트 dt는 50ms로 제한한다. FPS는 제한된 dt 대신 실제 프레임 간 시간으로 판단해야 한다. 낮은 draw call만으로 FPS 증가를 보장할 수 없다.

## 3. 적용한 배치 방식

`Queue`에 도형·텍스트 인스턴스를 호출 순서대로 쌓는다. 배치 하나에 최대 8개의 문자열 텍스처를 바인딩하고, 각 인스턴스가 사용할 슬롯을 지정한다. 단색은 슬롯 -1로 텍스처를 읽지 않는다. A 텍스처 → 단색 → B 텍스처 → A 텍스처도 슬롯 여유가 있으면 한 배치다.

분리 조건은 텍스처 슬롯 부족, 인스턴스 수 상한, 월드/HDR/UI 패스 경계다. 임의의 텍스처 정렬을 하지 않으므로 SceneGraph의 깊이 순서와 반투명 합성 순서를 유지한다. GLSL 3.30의 sampler 배열 제한에 맞춰 셰이더에서는 상수 인덱스 분기를 사용한다.

각 배치를 `glDrawArraysInstanced(GL_TRIANGLES, 0, 6, instanceCount)` 한 번으로 제출한다. 인스턴스가 1,000개여도 API 호출 카운터는 1이다. OpenGL 3.3에는 코어 base-instance 명령이 없으므로 배치마다 인스턴스 속성의 버퍼 시작 오프셋을 변경한다.

화면 밖 도형과 알파 0 도형은 큐 단계에서 제거한다. 이는 Actor 단계 컬링을 보완하며 장면 전체 순회나 좌표 계산까지 없애지는 않는다.

## 4. 파일 메시와 GPU 재사용

공유 토폴로지는 `Data/Meshes/unit_quad.mesh`의 정점 6개다. 시작 시 실행 파일 옆 `Cache/unit_quad_v1.mesh`를 먼저 읽고, 없거나 유효하지 않으면 패키지 메시를 읽어 캐시 파일을 저장한다. 패키지도 없거나 잘못되면 같은 정점을 메모리에서 생성한다. 캐시에는 식별자·버전·정점 수를 저장하고 좌표와 정점 순서까지 검증한다. 쓰기는 임시 파일과 교체 방식이며, 실패하면 메모리 메시로 진행한다.

GPU에는 이 정점 48바이트를 시작할 때 한 번 `GL_STATIC_DRAW`로 업로드한다. 매 프레임에는 사각형 모서리 4개, 색·발광, 텍스처 슬롯, 원형 여부로 구성된 인스턴스당 60바이트만 전송한다. GPU 스트림 버퍼는 용량을 재사용하고 orphan + subdata로 갱신한다. 드라이버 내부의 할당·대기까지 제거됐다는 의미는 아니다.

| 요청 1개 | 기존 CPU 정점 업로드 | 새 인스턴스 업로드 | 새 GPU 정점 수 |
|---|---:|---:|---:|
| Triangle | 108 B | 60 B | 6 (삼각형 하나는 퇴화) |
| Quad / Rect / Line / 문자열 | 216 B | 60 B | 6 |
| Ellipse | 2,160 B | 60 B | 6 |
| Glow (6개 원) | 12,960 B | 360 B | 36 |

위 수치는 구조에서 계산한 수치이며 FPS 실측값이 아니다. 글꼴 이미지 업로드·후처리 버퍼·CPU 컨테이너 메모리는 표에 포함하지 않는다.

현재 화면은 절차적 2D 도형으로 이루어져 있어 공통 쿼드로 표현했다. 건물마다 완성된 모델 파일을 저장하는 모델 캐시는 이번 범위에 포함하지 않는다. 위치, 카메라 투영, 애니메이션, 색상 변화는 계속 인스턴스 데이터로 계산한다. 캐시 형식은 이 쿼드 전용이며 임의의 3D 메시 로더가 아니다.

## 5. 시각적 변화와 비용의 교환

원은 기존 20각형 메시 대신 쿼드 내부의 원형 마스크로 표현한다. 원 둘레가 조금 달라지고 더 둥글어진다. 발광의 6겹 순서와 알파·발광 강도는 유지한다. 원 바깥 픽셀은 fragment shader에서 버리므로 CPU 삼각함수·정점 업로드는 줄지만 쿼드의 사각 영역까지 프래그먼트 처리가 발생할 수 있다. 큰 발광이 많은 장면에서는 GPU 픽셀 비용을 별도로 확인해야 한다.

Triangle은 남는 삼각형을 퇴화시켜 공통 메시를 사용한다. 삼각형만 많은 장면은 GPU 정점 수가 늘 수 있다. 반대로 원·발광이 많은 현재 장면에서는 제출 정점 수 감소가 예상된다. 이 예상은 `submitted_vertices`, `legacy_vertices`와 실제 프레임 시간으로 확인한다.

## 6. 기대하는 호출 수와 남는 호출

비어 있지 않은 월드와 UI가 각각 한 배치이고 기본 후처리가 활성화된 이론적 경우, 월드 1 + UI 1 + 후처리 13 = 15회다. 실제 장면은 텍스처 슬롯·인스턴스 용량에 따라 여러 배치로 나뉘므로 15회를 목표 보장값으로 사용하지 않는다.

기본 후처리 13회는 블룸 추출 1 + 블러 6 + 가장자리 다운샘플 1 + 블러 4 + 합성 1이다. 비네트는 합성 셰이더 안에서 처리한다. 설정 변경에 따라 달라진다. 후처리의 패스 수만 줄이기 위해 순서를 합치면 필터 결과가 달라질 수 있다.

`legacy_draw_estimate`는 현재 요청을 기존 인접 텍스처 규칙으로 묶었을 때의 월드+UI 호출 추정치다. 컬링 전 요청 기준이며 후처리는 제외한다. 실제로 구형 렌더러를 실행한 결과나 과거 FPS의 대체값이 아니다.

## 7. 지속적으로 남기는 분석자료

실행마다 고유 이름의 `.csv`와 `.log`를 만든다. CSV에는 매 프레임 호출/인스턴스/업로드/배치 분리/컬링/문자열 캐시/CPU 시간 자료를 기록한다. 콘솔은 1초 요약을 유지하고, CSV는 메모리에 모아 약 1초마다 저장한다. 마지막 잔여 자료는 종료 시 저장한다.

이벤트 로그에는 렌더러 버전, Debug/Release, GPU·드라이버 문자열, 메시 캐시 적중·재생성·저장 실패, GPU 버퍼 용량, 뷰포트와 후처리 설정 변화가 남는다. 기본 경로는 실행 파일 옆 `Logs`이며 폴더 생성이 안 되면 `%LOCALAPPDATA%/NeonVeil/Logs`를 시도한다. 최종 파일 쓰기 실패는 콘솔에 알리고 파일 기록만 중단한다. 실행 시 콘솔에 실제 경로를 출력한다.

자세한 열 정의와 분석 명령은 [PROFILING.md](../PROFILING.md)를 참고한다. 후속 변경마다 원본 로그와 분석 보고서를 함께 보관하고 장면·조작·설정·커밋을 메모한다. 사용자 로그 없이 개선 후 수치를 채우지 않는다.

## 8. 비교 절차

1. 같은 PC, 빌드 종류(성능 비교는 Release 권장), 창 크기, 줌, 후처리 설정에서 측정한다.
2. 정지 장면 30초, 청크 경계를 왕복하는 이동 30초, 전투·전리품·대화·거점 UI를 따로 기록한다. 시작 5초는 문자열 캐시 준비 구간으로 구분한다.
3. `batching.cfg`의 `texture_slots`를 1과 8로 바꿔 재시작하고 비교한다. 이 비교는 새 인스턴싱 경로에서 텍스처 배치 효과만 분리한다. 기존 렌더러 전체와의 A/B가 아니다.
4. `culling`을 0과 1로 바꿔 컬링 효과를 분리할 수 있다. F5/F6/F8로 후처리 기여를 확인할 때는 설정이 다른 구간을 섞어 평균내지 않는다.
5. 호출 감소와 함께 frame interval P95/P99, CPU render/submit, swap, 글꼴 캐시 miss를 비교한다. 겹치는 투명 건물·간판·비·원형 발광·공격 궤적·한글·UI·HDR 전환의 표시도 확인한다.

## 9. 다음 개선의 판단 기준

| 측정 결과 | 다음 후보 | 주의점 |
|---|---|---|
| texture_splits가 많음 | 한글 glyph atlas / texture array | 패딩·수명·갱신과 투명 순서 유지 |
| font_misses와 font_upload_bytes가 반복 증가 | 문자열 전체 캐시 대신 glyph 캐시 | 동적 수치 문구의 재래스터화 감소 |
| render_cpu_ms가 높고 submit은 낮음 | 정적 청크·건물 인스턴스 묶음 캐시, 공간 컬링 | 카메라·가림 투명도·리베이스 무효화 규칙 필요 |
| submit_cpu_ms가 높음 | 스트림 버퍼 링과 비동기 fence 관리 | GPU가 사용하는 영역을 덮어쓰지 않아야 함 |
| 후처리를 끄면 프레임 시간이 크게 줄음 | 해상도·블러 반경·패스 재설계, 비동기 GPU 타이머 측정 | 화질과 오버드로우를 함께 비교 |
| swap_ms가 큼 | VSync·창 합성·GPU 부하 측정 | CPU 타이머만으로 원인 확정 불가 |
| update_ms가 큼 | 충돌 검색·NPC·청크 갱신 분석 | 렌더링 호출 수와 별개의 비용 |

## 10. 확인 범위와 근거

이번 작업은 빌드·실행·GPU 셰이더 컴파일·성능 측정을 수행하지 않았다. 소스 형식, 프로젝트 등록, 메시 파일 구조 및 로그 스키마의 연결을 검토했다. 사용자 실행 로그가 확보되면 이 보고서의 예상과 실제 결과를 구분하여 후속 보고서를 추가한다.
